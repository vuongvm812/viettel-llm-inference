# Round-1.2 Latency Optimization: Hopper Kernels, Zero-Copy IPC, Rust Scheduler, MIG Mitigations

## Context

Round-1.2 serves LFM2.5-1.2B-Instruct (16 layers: 10 short-conv + 6 GQA, hidden 2048) on an H200 MIG 1g.18gb slice (16 SMs, 18 GB, ~600 GB/s, 3 vCPUs). Scoring: ERS with TPOT floor 1ms/ceiling 10ms, TTFT 10/400ms — 1ms TPOT ≈ 28ms TTFT. Current stack: `vllm/vllm-openai:v0.25.0` (+ team fork image) + `vtl` plugin (`round-1.2/vtl/`) with `--quantization=vtl_w4a8` (online RTN pack into vLLM's SM90 CUTLASS kernel), Rust frontend (`vllm-rs`) active, FULL_AND_PIECEWISE cudagraphs, V2 model runner forced.

The user requested investigation + implementation plan for three optimization areas. Investigation is complete (3 exploration agents + 1 design agent + external verification). This plan records what is **already implemented** (with references) and the implementation plan for the gaps, split into **5 workstreams implemented by 5 parallel Opus sub-agents**. User decisions locked in: **iceoryx2** for IPC (disruptor-rs is intra-process-only, cannot span the frontend/EngineCore process boundary), **full Rust scheduler/block-metadata port** (logic-preserving), **both kernel phases unconditional**.

## Execution model (per user feedback)

- **Step 0:** write this plan (investigation findings + all WS specs) to `docs/round-1.2-latency-optimization-plan.md` in the repo (create `docs/` if missing).
- **Step 1:** spawn **5 sub-agents (model: Opus 5) in parallel**, one per workstream below, each with `isolation: worktree` so they cannot conflict (known file overlaps: `round-1.2/Dockerfile` is touched by WS2+WS3, root `Makefile` by WS1+WS2 — the orchestrator resolves these at merge). Each agent gets its full WS spec from the docs file plus the shared constraints section.
- **Step 2:** after all 5 complete, the orchestrator merges the worktrees into a branch (resolving the Dockerfile/Makefile overlaps), then invokes the **`code-review` skill** on the combined diff with an explicit latency lens: no per-step heap allocation on hot paths, no graph breaks under `torch.compile`, no busy-spin threads on the 3-vCPU budget, everything env-gated default-off, submission compose literals-only. (If only the user-triggered `/code-review ultra` variant is available in-session, fall back to an adversarial multi-agent review pass and tell the user they can run `/code-review ultra` on the branch.)
- **Step 3:** orchestrator fixes review findings, runs the full off-box verification suite, and reports the completed merged state.

**No mid-way measurement pauses.** Every workstream is implemented to full completion in one pass — no stop-losses, no "continue after A/B" checkpoints, no waiting on user measurements. All runtime decisions (which schedule, which transport, which scheduler authority) are deferred to env gates, so on-box measurement can happen at any time afterward without blocking or reordering any implementation work.

### Shared constraints (given to every sub-agent)
- Served stack is v0.25.0; the local `./vllm` checkout is post-v0.26.0 main but the relevant kernel/engine files are verified byte-identical or the v0.25.0 line numbers are given below. Never edit `./vllm` (gitignored dev checkout) — deliverables are vtl patches, vtl csrc, `vtl/vllm_patches/*.patch` files, Dockerfiles, Makefile.
- Every feature env-gated, default-off. Loggers must be children of `vllm.vtl` (bare `vtl` loggers are silently dropped). No `${VAR}` interpolation in `docker-compose.yaml`. A/B discipline: 3 boots/arm, `bench/ab_summary.py`, ~0.5ms boot-to-boot TPOT noise floor.
- Off-box only (no GPU): `make check` must pass; Docker build is the CUDA/Rust compile test.

## WS1 — Stock-schedule sweep harness (agent 1, small)

Extend the existing `make sweep-schedule` (root `Makefile:~285`) to cover **all 10 stock `VTL_W4A8_SCHEDULE` values** (currently sweeps only `heuristic 128x16_1x1x1 128x32_1x1x1 128x256_1x1x1`), 3 boots/arm, decode-heavy open-loop trace via `bench/replay.py`, results through `bench/ab_summary.py` with per-run noise-floor readout. Add v2-schedule awareness: when an arm name matches a v2 pattern (`*_sk`, `*_pp`, `128x8*`, `*_2x1x1` beyond the stock set), export `VTL_W4A8_SCHEDULE_V2` instead of `VTL_W4A8_SCHEDULE` (coordinates with WS2's env contract; the WS2 spec defines the names). Also emit a per-arm microbench-first mode so kernel-level filtering (`make bench-kernel`) runs before full boots. Note in the target's help text: flipping schedule envs invalidates `/opt/vtl/cache` AOT caches — first boot per arm pays compile.

Files: root `Makefile`; possibly a small `bench/sweep_report.py` if `ab_summary.py` needs a multi-arm table mode. Effort ~0.5–1 dev-day.

## WS2 — `vtl._C_w4a8` CUDA extension: Stream-K, cluster, small-tile schedules (agent 2)

Second CUDA extension compiled `sm_90a`-only (separate .so so a non-Hopper load failure can't take down `vtl._C`), registering `vllm_cuda::w4a8_mm_v2` with an in-op M-threshold branch: M≤32 (env `VTL_W4A8_V2_MTHRESH`) → named v2 schedule; M>32 → forward to stock `_C::cutlass_w4a8_mm` via `torch::Dispatcher::findSchemaOrThrow` (prefill untouched, single opaque op → no torch.compile graph breaks).

**Files:**
- Create `round-1.2/vtl/csrc/w4a8/w4a8_mm_v2.cu` — vendored from `csrc/libtorch_stable/quantization/cutlass_w4a8/w4a8_mm_entry.cu` (verified byte-identical v0.25.0↔HEAD), converted to regular ABI (`at::Tensor`; the stable-ABI epilogue header `scaled_mm_epilogues_c3x.hpp` is dual-mode via `#ifdef TORCH_TARGET_VERSION` — copy verbatim into `vtl/csrc/w4a8/cutlass_extensions/epilogue/` keeping include paths). Drop pack/encode ops (stock `_C` ops still do weight prep at load). Generalized template adds `KernelSchedule/EpilogueSchedule/TileScheduler` params; Stream-K arm forces `DecompositionMode::StreamK` (the heuristic degenerates to DataParallel on small grids otherwise). Local ~10-line `CUTLASS_CHECK`; hardcode out dtype `at::kBFloat16`.
- Instantiations (each an isolated `using` + dispatch string so a static_assert drops one arm, not the build): `128x16_1x1x1_sk`, `128x32_1x1x1_sk` (Stream-K cooperative — strongest hypothesis for w2's 64 k-iter single wave and qkv's ragged 1.5 waves), `128x16_2x1x1` (cluster multicast; honest note: after swap+transpose the multicast operand is the *activation*, small at decode — sweep it anyway per scope decision), `128x8_1x1x1` (GMMA atom N=8 is legal; CollectiveBuilder may reject — attempt, drop on assert), `64x16_1x1x1_pp`/`64x32_1x1x1_pp` (Pingpong for TileM=64 — cooperative requires TileM∈{128,256}; **speculative**: upstream comments the cooperative epilogue is the only one supporting swap+transpose; parity-gated, plan does not depend on it).
- Modify `round-1.2/setup.py` (second `CUDAExtension` gated on `CUTLASS_DIR` env, skipped silently when absent; `-gencode arch=compute_90a,code=sm_90a` — overrides `TORCH_CUDA_ARCH_LIST`; no PTX, deliberate), `round-1.2/Dockerfile` (CUTLASS **v4.4.2** tarball — vLLM pins v4.4.2 via FetchContent and headers do NOT ship in the image or wheel; single layer, headers removed after build; extend the existing cuobjdump arch assert to the new .so), `round-1.2/vtl/patches/quant_w4a8.py` (per-shape env map `VTL_W4A8_SCHEDULE_V2="n3072k2048=128x16_1x1x1_sk;...;*=..."` validated against the legal set, resolved once at load into `layer._vtl_w4a8_v2` — static per layer, no graph break; `torch.library.register_fake` returning `a.new_empty((m,n),bf16)`, same pattern as existing fakes ~line 329).
- Registration: `TORCH_LIBRARY_FRAGMENT(vllm_cuda, ...)` with enforced `import vtl._C` first; fall back to own namespace `TORCH_LIBRARY(vtl_w4a8, ...)` if load-order proves fragile. Boot-time tiny-mm probe at patch install so wrong-arch fails at boot, not mid-benchmark (same discipline as `warmup_healthcheck`). Runtime gate: capability == (9,0) exactly.
- Create `round-1.2/bench/test_w4a8_v2.py` — parity (all v2 schedules × LFM2 shapes {(3072,2048),(2048,2048),(16384,2048),(2048,8192),(6144,2048),(65536,2048)} × M∈{1,4,8,16,33,512} vs stock; allclose rtol/atol 1e-2 for Stream-K since K-reduction order changes, bit-exact for the M>threshold arm) + CUDA-event microbench table; auto-picked-up by `make test-kernel`/`bench-kernel` globs.

## WS3 — iceoryx2 zero-copy IPC: frontend ↔ EngineCore (agent 3)

disruptor-rs cannot span processes; **iceoryx2** (user-selected) is zero-copy lock-free shm IPC, Rust-native core with released Python bindings on PyPI (pinned **0.9.3** in `round-1.2/Dockerfile`, which must equal the `iceoryx2` crate version in the Rust patch — the two halves share a shm data-segment layout), pub/sub + request/response + event patterns, no central daemon. Both processes share one container.

**Phase A (this WS): transport swap, serialization unchanged** — msgpack bytes written into loaned shm buffers (encode-once, zero-copy transport). Keep ZMQ alive for handshake/registration (`EngineCoreReadyResponse`), `ENGINE_CORE_DEAD` sentinel, and as fallback. Env-gated `VTL_SHM_IPC=1`, default off.

- **Services:** `vtl/req` (Rust pub → Py sub; ALL request types through this one channel — aborts must not pass adds, per `core.py`'s own ordering comment) and `vtl/out` (Py pub → Rust sub); slice-payload publishers (dynamic size; worst-case ADD ≈ 600KB msgpack). **Event pattern** (listener/notifier + WaitSet) for wakeups — critical on 3 vCPUs: no busy-spin readers, threads park.
- **Rust** (ships as a new patch in `round-1.2/vtl/vllm_patches/rust-frontend/`, built by `Dockerfile.vllm-fork`; `cargo add iceoryx2` to the workspace): the transport seam is exactly 3 touch points — `ClientInner.input_send` (`engine-core-client/src/client/imp.rs:30-31`), the single `transport::send_message` call (`imp.rs:226-232`), the `run_output_loop` spawn (`client.rs:297`). Add `enum InputSink { Zmq(RouterSendHalf), Shm(...) }`; an iceoryx2 output-subscriber thread feeds the same mpsc as the ZMQ loop, which stays running as the free death-detector.
- **Python** (pure vtl monkeypatch — `general_plugins` loads in the EngineCore process too; no source .patch needed): new `round-1.2/vtl/patches/shm_ipc.py`, `default=False`. (1) Wrap `EngineCoreProc.__init__`: start one extra input thread (iceoryx2 subscriber + `MsgpackDecoder`, same construction as `core.py:1484-1497`, `input_queue.put_nowait` — `queue.Queue` is thread-safe so the ZMQ input thread stays untouched; replicate the ADD `preprocess_add_request` try/except and ABORT dual-queue put by calling the same methods). (2) Replace `process_output_sockets` with a copy whose only transport line changes from `sockets[client_index].send_multipart(buffers...)` to an iceoryx2 publish of `b"".join(buffers)` (assert `len(buffers)==1` — multi-frame is zmq tensor zero-copy that text-only outputs don't produce; fall back to ZMQ send otherwise), plus a DEAD record on shutdown alongside the existing ZMQ sends. `pip install iceoryx2` in `round-1.2/Dockerfile`.
- **Failure modes:** engine death → ZMQ sentinel path unchanged; Rust death → launcher sentinel unchanged (`v1/utils.py:405-430`); stale shm → iceoryx2 service lifecycle + fresh names per boot; flag off → zero code active.
- **Tests:** Rust↔Python golden framing/compat test (runs in-container, no GPU); kill-engine integration test (frontend 503s + launcher exit, matching ZMQ behavior); idle-CPU soak assert (<1% via `docker stats`).

**Honest sizing (stated up front, not a reason to skip):** ZMQ UDS costs ~30–80µs/message; one output message per step → direct TPOT ~0.02–0.06ms, below the 0.5ms floor. The larger expected effect is indirect — fewer syscalls/wakeups contending for 3 cores (~10 tokio + 3 Python threads today). An isolated transport microbench ships as part of the test suite for later on-box use; it does not gate implementation.

**Phase B (implemented in the same pass, not deferred):** fixed-layout zero-copy structs for the **output path** (the per-step hot path — `EngineCoreOutputs` at decode is small and regular: request id, new token ids, finish flags), env-gated `VTL_SHM_IPC_RAW=1` layered on top of Phase A: Python packs a flat little-endian struct directly into the loaned buffer (`struct.pack_into`, no msgpack), Rust reads it with a `#[repr(C)]` view — no deserialization allocation. Request path stays msgpack (large, irregular, off the per-step path). Fall back to Phase A framing for any output that doesn't fit the fixed layout (logprobs, multi-frame). Effort ~5 dev-days total for the WS.

## WS4 — Full Rust scheduler / block-metadata port, logic-preserving (agent 4)

User-selected full scope. Architecture: **PyO3 extension crate inside the EngineCore process** (not cross-process — SchedulerOutput consumers are in-process; a process hop would add IPC where none exists). New crate `round-1.2/vtl-sched/` (maturin-built wheel installed in the Dockerfile), exposed as Python module `vtl_sched`. Staged with a **shadow-mode parity gate** — this replaces the most correctness-critical component, and LFM2's hybrid layout raises the bar: attention + short-conv KV groups (`v1/core/single_type_kv_cache_manager.py` incl. the mamba manager; the radix branch's M5 warning "hybrid mamba clamp — getting this wrong = silent output corruption" applies here too).

- **R0 — boundary + skeleton (2d):** Rust API surface = the `KVCacheManager` interface consumed by `v1/core/sched/scheduler.py` (~10 methods: `get_computed_blocks`, `allocate_slots`, `free`, `cache_blocks`, usage/stats) wrapping `BlockPool` internals. Zero-copy output: Rust owns the block-ID arrays, exposed as numpy views via `rust-numpy` (no per-step copies), feeding the V2 runner's existing `BlockTables.append_block_ids` staged-write API unchanged. Stack-allocation discipline: fixed-capacity arenas sized from the startup KV budget, `SmallVec` for per-request block runs, zero per-step heap allocation on the hot path.
- **R1 — BlockPool + prefix cache (4–5d):** free-queue (`FreeKVCacheBlockQueue` doubly-linked LRU), `BlockHashToBlockMap`, refcounts, eviction, `cache_full_blocks`/`cache_partial_block`. **Hash parity is mandatory**: port vLLM's exact block-hash function (init seed, token-chunk hashing incl. extra-keys) and verify against Python on recorded traces — a mismatch silently zeroes the 82.8% prefix-hit rate. Block granularity first (vLLM's map is already radix-equivalent there); token-granular matching from the `radix-attention-port` branch as a flag-gated variant.
- **R2 — hybrid managers (3–4d):** port the per-spec managers for full-attention + short-conv groups (`kv_cache_coordinator.py`, `single_type_kv_cache_manager.py`), including mamba state-slot semantics and the conv prefix-cache clamp rules (`find_longest_cache_hit` for mamba; align-mode conv caching is live on this stack).
- **R3 — shadow mode (2d + soak):** `VTL_RUST_SCHED_SHADOW=1` runs Rust alongside Python every scheduler call, asserting identical outputs (block IDs, computed-block counts, eviction victims) across the full 420-req trace replay + closed-loop runs. Any divergence is a bug by definition (logic-preserving port).
- **R4 — flip authority (1d):** `VTL_RUST_SCHED=1` makes Rust authoritative via monkeypatched `KVCacheManager` construction (seam demonstrated by existing `vtl/patches/kv_cache_manager.py` subclass). Measured-budget honesty: Python scheduler+KV-manager cost is ~0.3–0.6ms/step of a ~5–7ms dev-box step and the on-box host gap is ~0.6ms/step total — the win is a fraction of that; shadow infra is what makes it safe to ship default-off regardless.
- **R5 — scheduler loop port (implemented in the same pass):** port `schedule()` itself (waiting/running queues, token-budget loop, the cache-aware SJF policy from `sched_policy.py`), env-gated `VTL_RUST_SCHED_FULL=1`, same shadow-parity harness extended to full `SchedulerOutput` comparison.

Effort ~3 person-weeks R0–R5, implemented end-to-end by the sub-agent in one pass — shadow-parity tests run off-box against recorded traces (`data/input/trace-round2.jsonl` replayed through the mock engine), so correctness validation does not wait on the H200. Top risks: hybrid conv-cache semantics (R2 ports tests first, shadow gate), hash/eviction-order parity (golden traces), PyO3 boundary chatter (batch calls, numpy views not lists).

## WS5 — L2 persistence probe + KV alignment asserts (agent 5, small)

- 5-line CUDA probe (small helper in `vtl/csrc/` or ctypes-on-libcudart in `warmup_healthcheck` / a `make` target): `cudaDeviceGetAttribute(cudaDevAttrMaxPersistingL2CacheSize)` + `cudaDeviceGetLimit(cudaLimitPersistingL2CacheSize)` logged at boot. Expected 0 on the slice (docs: L2 set-aside disabled under MIG). **If nonzero** (docs wrong or judge not actually MIG): implement `cudaStreamSetAttribute` + `cudaAccessPolicyWindow` over the hot per-layer weight buffers (w2 8MB + w13 16MB int4 — pinnable scale vs. the slice's L2 partition) on the decode stream via a vtl `_C` helper, env-gated, A/B as usual. Also add `CUDA_DEVICE_DEFAULT_PERSISTING_L2_CACHE_PERCENTAGE_LIMIT` to compose comments as the MPS-style fallback knob (harmless if ignored).
- **Default-on exception to "everything env-gated default-off":** the probe half registers with `default=True` (`VTL_ENABLE_L2_PERSIST`). It is two read-only CUDA attribute queries inside the existing `load_model` wrapper — it changes no device state and answers the question this WS exists to ask, so gating it off would mean the answer never arrives. The half that *writes* device state (the set-aside limit + the access-policy window) stays opt-in behind `VTL_L2_PERSIST=1`, default off.
- One-time assert (test, not runtime): KV `page_size_bytes % 128 == 0` and flat-tensor base 256B-aligned for every KV group — documents that point 2c is satisfied; catches regressions if block_size/dtype changes.

Effort ~0.5 dev-day.

## Explicitly out of scope (rationale recorded, not dismissed)

- **Cross-step persistent megakernel** (ring-buffer work fetch): duplicates FULL cudagraph (1 launch/step, 0.26ms host) and CUTLASS's persistent tile scheduler; would mean replacing the entire captured graph with a hand-scheduled resident kernel — months. Revisit only if WS2 shows launch/tail-wave overhead surviving Stream-K.
- **disruptor-rs**: intra-process only; superseded by iceoryx2 per user decision.
