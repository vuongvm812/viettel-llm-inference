04 · prefill & decode1:30

Prefill & decode

Prompt tokens all exist up front → processed in one big parallel pass. After that: one pass per new token, forever.

prefill: whole prompt, one pass → TTFT = how long until the answer starts decode: one token per pass → ITL = the "typing speed" users feel
prefill = compute-heavy, parallel decode = thousands of tiny sequential steps

05 · memory-bound decode1:30

Memory-bound decode

One decode token = streaming every model weight from GPU memory for a tiny bit of math. Bandwidth sets the speed, not FLOPs.

■7B model @ fp16 ≈ 14 GB of weights — read every step
■A100 HBM ≈ 2 TB/s → ~140 tok/s ceiling at batch = 1 (back-of-envelope)
batch = 1 — low on the bandwidth-bound slope, compute idle
batch = 32 — near saturation: same weight read, 32× the tokens
■x-axis "arithmetic intensity" = math done per byte moved — decode is far left
decode speed ≈ bandwidth ÷ bytes moved batching is nearly free throughput

the "v" in vLLM = virtual memory — this idea named the whole project

09 · continuous batching2:00

Continuous batching

Before every forward pass the scheduler rebuilds the batch: finished requests leave, waiting ones join — prefill and decode run together.

prefill decode blank = not in the batch
join instantly, leave instantly all tokens flattened into one GPU pass GPU never waits for the slowest request long prompt? chunked prefill splits it across steps — no one stalls

13 · speculative decoding1:00

Speculative decoding

The token loop is serial (slide 3). Trick: a tiny draft model proposes k tokens; the big model verifies them all in one pass — accepted guesses are free speed.

draft modelcheap, guesses k tokens
→ t1t2t3t4 →
big modelONE verify pass
→ t1 ✓t2 ✓t3 ✓t4 ✗
3 tokens for the price of 1 big pass · rejected → resampled, loop continues
output provably identical to the big model alone wins only when the draft guesses well vLLM drafts: n-gram, EAGLE, Medusa
14 · cuda graphs & host overhead1:00

CUDA graphs & host overhead

Each decode step is ~ms of GPU work — but the Python host must schedule, sample, and launch every kernel between steps. Those gaps add straight to ITL.

EAGER — host work before every launch
CUDA GRAPHS — record once, replay every step
GPU forward passhatched = host (Python + kernel launches)
thousands of kernel launches → one graph replay matters most at small batch / short steps vLLM captures graphs at startup
15 · latency vs throughput1:30

The latency–throughput tradeoff

Bigger batches buy throughput until the GPU saturates; past that point, every request's tokens arrive slower. Chat UIs live left of it, batch pipelines right.

1 one token at a time 2 prefill ≠ decode 3 KV cache = the scarce resource 4 PagedAttention = virtual memory 5 continuous batching keeps the GPU full

not covered today: multi-GPU serving — tensor/pipeline parallelism, disaggregated prefill/decode
